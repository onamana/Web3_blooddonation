# ChainLab — 블록체인 이해부터 해커톤 실전까지

## 시작

웹앱 주소: http://localhost:5173/learn

`Web3_blooddonation/frontend` 폴더에서 `npm run dev -- --host 127.0.0.1`로 실행합니다. 기존 헌혈 화면은 /donor와 /hospital에 있습니다. 웹앱은 설치된 React/Vite 환경을 사용합니다.

학습 진도와 노트는 브라우저 localStorage에 저장됩니다. 브라우저 데이터 삭제나 다른 기기로의 이동 시 자동 동기화되지 않습니다. 사이드바의 학습 기록 내보내기로 Markdown을 보관하세요. 실험실은 실제 SHA-256 계산과 교육용 체인 비교·가스 계산이며 Solidity 컴파일러나 실제 블록체인 노드는 아닙니다.

## 6주 학습 운영

권장 주 6–10시간. 기간은 사전 지식에 따라 조정하며, 모든 블록체인 분야의 숙련을 보장하는 기간은 아닙니다. 우선 EVM 기반 앱을 혼자 설계·구현·검증하는 것을 목표로 합니다.

| 주 | 웹앱 모듈 | 실습 증거 |
|---|---|---|
| 1 | 1–2: 필요성·암호학 | DB 대안 비교, 변조 실패, 머클 포함 증명 |
| 2 | 3–4: 거래·Solidity | 거래 필드 설명, 발급/조회/폐기 구현 |
| 3 | 5: 가스·테스트 | 정상/실패 경로 테스트, 배포 주소 |
| 4 | 6–7: 지갑·보안 | 거래 상태 UI, 위협 모델, 공격 방어 테스트 |
| 5 | 8: DID/VC | 정보 흐름도, 발급기관 신뢰·폐기 검증 |
| 6 | 9: 운영·완주 | E2E 데모, ADR, 발표, 운영 한계 |

각 모듈은 읽기 → 직접 실험 → 퀴즈 → 산출물 → 3분 설명 순서로 진행합니다. 퀴즈 통과는 지식 확인일 뿐 실습 완료 인증은 아닙니다. 하루 끝에 노트에 실패한 가설과 수정 근거를 한 줄 남기세요.

프로젝트 최상위 `학습자료/0주차`에는 해시·커밋먼트·전자서명·머클트리 실습이 있습니다. README를 읽고 `npm install`, `npm test`, `npm run lab:hash`, `npm run lab:sign`, `npm run lab:merkle` 순서로 진행합니다. 설치에는 사용자의 네트워크 환경이 필요합니다.

## 설치 없이 컨트랙트 실행: Remix VM

1. https://remix.ethereum.org 에서 새 Solidity 파일을 만들고 함께 제공한 CredentialRegistry.sol 내용을 넣습니다.
2. Solidity Compiler에서 0.8.24 이상 0.9 미만의 안정 버전을 선택하고 컴파일합니다. 예제를 배포한 컴파일러·EVM 대상·최적화 설정을 기록합니다.
3. Deploy & Run에서 Remix VM을 선택합니다. 첫 번째 계정 A로 Deploy합니다. VM은 브라우저 안의 가상 체인이며 실제 ETH를 쓰지 않습니다.
4. issue에 다음 교육용 값을 입력합니다. 실제 개인정보 해시를 쓰지 마세요.

```
id: 0x1111111111111111111111111111111111111111111111111111111111111111
commitment: 0x2222222222222222222222222222222222222222222222222222222222222222
expiresAt: 4102444800
```

expiresAt는 Unix 초 단위이며 예시 값은 2100년 시작입니다. 실제 서비스에서는 짧고 의미 있는 만료 정책을 정하세요.

5. isValid(id)가 true인지 확인합니다. getCredential(id)의 발급자·만료·커밋먼트를 확인합니다.
6. 같은 id로 다시 issue하면 AlreadyExists가 발생해야 합니다.
7. 계정 B로 전환해 다른 id를 issue하면 Unauthorized가 발생해야 합니다. A의 id를 revoke해도 Unauthorized여야 합니다.
8. A로 돌아와 revoke(id)를 호출한 뒤 isValid(id)가 false인지 확인합니다.

### 추가 검증표

| 시나리오 | 예상 |
|---|---|
| A만 setIssuer(B,true)를 실행 | 성공 |
| B가 setIssuer 실행 | Unauthorized |
| B 허용 후 새로운 id 발급 | 성공 |
| zero id 또는 zero commitment | InvalidInput |
| expiresAt=1 | InvalidInput |
| 존재하지 않는 id 조회 | getCredential은 NotFound, isValid는 false |
| 이미 폐기한 id 다시 폐기 | AlreadyRevoked |
| 발급자 B 비활성화 후 새 발급 | Unauthorized |
| B 비활성화 후 기존 증빙 조회 | 만료·폐기되지 않았다면 여전히 유효 |
| B 비활성화 후 자기 증빙 폐기 | 가능 |

마지막 두 정책은 의도적인 설계입니다. 발급기관 자격 해제가 기존 증빙까지 무효화해야 한다면 isValid 정책과 테스트를 함께 변경하세요. 관리자 교체·긴급 정지·복구·외부 표준 VC 검증은 예제 범위 밖입니다. 이 계약은 간단한 증빙 레지스트리이며 W3C VC 완전 구현이 아닙니다. ID는 허용 기관끼리 충돌하지 않게 발급기관 주소·nonce·chainId를 포함해 생성하는 방식으로 확장할 수 있습니다.

## 테스트넷 배포

현재 Ethereum 공식 네트워크 안내에서 앱용 테스트넷을 확인합니다: https://ethereum.org/developers/docs/networks/

학습 시 확인한 문서는 Sepolia를 앱용 기본 테스트넷으로 안내합니다. 지원 상태는 배포 직전에 다시 확인하세요. 테스트 전용 지갑을 만들고 공식 안내에 연결된 faucet에서 테스트 ETH를 구합니다. Remix의 지갑 제공자 환경으로 전환한 뒤 지갑의 네트워크를 직접 확인하고 Deploy를 승인합니다. 이 웹앱 자체는 지갑 접근이나 배포를 실행하지 않습니다.

기록할 항목: 네트워크 이름, chainId, 계약 주소, ABI, 배포 거래 해시, receipt status, 컴파일러 버전, optimizer/EVM 설정, 배포 시각. 탐색기에서 코드 검증 후 다른 계정으로 발급 불가와 증빙 조회를 다시 확인합니다. Sepolia chainId는 11155111입니다.

## dApp 연결 예시 (viem)

이 예시는 별도의 dApp 프로젝트에 viem을 설치한 뒤 적용하는 코드입니다. 학습 웹앱에는 viem 설치를 요구하지 않습니다. 현재 API는 공식 문서와 사용 중인 버전을 함께 확인하세요.

```ts
import { createPublicClient, createWalletClient, custom, http, parseAbi } from 'viem';
import { sepolia } from 'viem/chains';

const abi = parseAbi([
  'function issue(bytes32 id, bytes32 commitment, uint64 expiresAt)',
  'function isValid(bytes32 id) view returns (bool)',
  'function revoke(bytes32 id)',
]);
// provider는 사용자가 선택한 EIP-1193 지갑 제공자.
// address는 실제 배포한 주소, rpcUrl은 Sepolia HTTP RPC 주소.
const publicClient = createPublicClient({ chain: sepolia, transport: http(rpcUrl) });
const wallet = createWalletClient({ chain: sepolia, transport: custom(provider) });
const [account] = await wallet.requestAddresses();
if (!account) throw new Error('지갑 계정이 없습니다.');
if (await wallet.getChainId() !== sepolia.id) throw new Error('Sepolia로 전환하세요.');

const { request } = await publicClient.simulateContract({
  address, abi, functionName: 'issue', account,
  args: [id, commitment, BigInt(Math.floor(Date.now() / 1000) + 86400)],
});
const txHash = await wallet.writeContract(request);
// 이 시점 UI: 거래 제출됨, 확인 중
const receipt = await publicClient.waitForTransactionReceipt({ hash: txHash });
if (receipt.status !== 'success') throw new Error('거래 실행 실패');
const valid = await publicClient.readContract({ address, abi, functionName: 'isValid', args: [id] });
// valid를 화면에 표시. receipt 확인과 서비스가 요구하는 최종 확정 정책은 별개.
```

주소, id, commitment는 viem의 Address/Hex 타입과 길이 검증을 적용하세요. 지갑 제공자는 EIP-6963 탐색 또는 선택한 지갑 라이브러리로 받습니다. 사용자의 서명 거절, account/chain 변경, RPC 시간 초과, revert를 각각 처리하고 대기 중 재제출을 막습니다. receipt 대기 시간 초과가 거래 실패를 뜻하지는 않으므로 해시로 다시 조회할 수 있게 하세요. 개인키를 브라우저 코드에 넣지 않습니다.

## 해커톤 기획 카드

문제: 여러 기관이 발급한 증빙을 수신기관이 검증하기 어렵다.
사용자: 발급기관 담당자와 증빙 검증 담당자.
MVP: 발급 → 검증 → 폐기 → 무효 확인.
온체인: 기관 권한, 커밋먼트, 만료·폐기 상태.
오프체인: 원문 증빙, 개인 식별 정보, 암호화 자료, 접근 로그.
위협: 무권한 발급, 기관 키 탈취, 중복 발급, 개인정보 추측, UI의 잘못된 성공 표시.
방어 증거: 실패 테스트, 역할 분리, nonce/ID 정책, 데이터 최소화, receipt+상태 조회.
한계: 기관의 거짓 입력, 관리자 권한, RPC 의존, 네트워크 장애, 실서비스 감사 미완료.

대회 심사 기준은 주최 측 공식 안내에 맞춥니다. 예제 채점표: 문제·필요성 20, 실제 동작 30, 테스트·보안 20, UX 15, 설명·재현성 15. 이것은 학습용 자체 평가표이며 특정 대회의 공식 배점이 아닙니다.
